§ 03.2 · Étage 3 — Le point critique

L'étage le plus délicat

Étage 03 · Constraints.

Le LLM doit lister toutes les contraintes — y compris celles que l'énoncé ne dit pas mais que le solveur a besoin d'entendre.

Étude de cas · N-Queens
L'énoncé dit : « placer N reines, aucune ne s'attaque ».
EXPLICITE
· une reine par ligne
· une reine par colonne
IMPLICITE (souvent oublié)
· diagonales différentes
Schéma de sortie · Constraint
class Constraint(BaseModel):
  name:        str
  kind:        ConstraintType   # AllDifferent, Sum, ...
  explicit:    bool
  pseudo_code: str
  scope:       list[VariableRef]
  # validé par Pydantic ↓

Chaque contrainte est classifiée par type CP-SAT et décrite par une formule en pseudo-code.
→ servira plus tard à  la vérification sémantique.

§ 03.3 · Étage 4 — Codegen

Génération finale

Variables + Contraintes
⟶ Script Python.

L'étage 4 ne raisonne plus sur le problème — il traduit les artefacts structurés des étages précédents en code ortools.sat.python exécutable.

Contrat de sortie
  • Une fonction solve()  au top-level 
  • Retour structuré: { "status": ..., "values": ... }
  • Pas d'effet de bord
  • Exécutable en sous-processus isolé
Forme attendue · N-Queens
from ortools.sat.python import cp_model

def solve(N: int = 8) -> dict:
    model = cp_model.CpModel()

    queens = [model.NewIntVar(0, N-1, f"q_{i}")
              for i in range(N)]

    model.AddAllDifferent(queens)
    model.AddAllDifferent(queens[i] + i for i in range(N))
    model.AddAllDifferent(queens[i] - i for i in range(N))

    solver = cp_model.CpSolver()
    status = solver.Solve(model)
    return {
        "status": solver.StatusName(status),
        "values": [solver.Value(q) for q in queens],
    }

§ 04 · Vérification

Vérification en cascade · 3 niveaux

Le code généré passe trois filtres,
du plus simple au plus exigeant.

NIVEAU 01
Syntaxique

Le code parse-t-il sans SyntaxError ?

↳ ast.parse()
NIVEAU 02
Faisabilité

Le solveur retourne-t-il OPTIMAL ou FEASIBLE ?

↳ subprocess isolé · timeout · capture runtime
NIVEAU 03
Sémantique

La solution respecte-t-elle les contraintes formalisées à  l'étage 3 ?

↳ ré-évaluation des pseudo-formules sur les valeurs
▸ INSIGHT
C'est la vérification sémantique qui rattrape les cas où « le solveur a trouvé une solution, mais ce n'est pas la solution du bon problème ».

§ 04.1 · Boucle de réparation

Réparation auto-supervisée

En cas d'échec, on réinjecte l'erreur
et on monte la température.

Boucle · max 3 tentatives
TRY 1
T = 0.0
déterministe
→
TRY 2
T = 0.5
exploration
→
TRY 3
T = 1.0
divergence
prompt[retry] = base_prompt
+ failing_code
+ error_message
+ aucun indice ciblé
Choix méthodologique
Le prompt de retry reste générique — on ne dit pas quoi corriger.
On veut mesurer la capacité naturelle du LLM à  se corriger lui-même, sans aide.
La température croissante évite que le LLM
reproduise exactement le même code défaillant.

§ 06.5 · Étude de cas — un échec C7

Bin Packing · code généré par le LLM

ÉCHEC NIVEAU 2 · FAISABILITÉ

Le LLM généralise depuis la syntaxe Python ordinaire —
sans intégrer la sémantique du DSL CP-SAT.

Code produit
for j in range(n_objets):
  model.Add(
    sum(
      tailles_objets[i] * (boite_objet[i] == j)
      for i in range(n_objets)
    ) <= capacite_boite
  )
model.Minimize(max(boite_objet) + 1)
ERREUR RUNTIME

unsupported operand type(s) for *:
'int' and 'BoundedLinearExpression'

Diagnostic · 2 fautes C7
FAUTE 01

(boite_objet[i] == j) n'est pas un booléen mais une BoundedLinearExpression — non multipliable par un int.

↳ Correct : réifier avec un BoolVar + OnlyEnforceIf.

FAUTE 02

max(boite_objet) applique le max natif Python à des IntVar — ne contraint rien.

↳ Correct : model.AddMaxEquality(...).

↳ Exactement le type d'erreur qu'un humain familier d'ortools n'écrirait jamais.

§ 08 · Conclusion

Ce que ce projet nous a appris

Décomposer en étages est la bonne approche —
non seulement pour la qualité, mais pour
pouvoir attribuer les erreurs.

Bilan
  • Les étages analytiques sont gérés correctement sur problèmes standards
  • Le vrai défi reste la complétude des contraintes implicites
  • La boucle de réparation améliore mais ne remplace pas une modélisation rigoureuse
  • L'attribution par étage est indispensable pour analyser les limites du LLM
